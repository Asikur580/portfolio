Migrating live financial data with zero mismatch

Asikur Rahman Sep 2026 6 min read

Rebuilding Radiant Agrovet's ERP — 19 modules and 117 pages, Laravel 13 with a React 19 front end — was the visible part of the project. The risky part was moving thousands of live invoices, payments and customers out of the legacy PHP system without corrupting a single balance.

Zero tolerance means you need proof

"The migration looks fine" is not good enough for money. I set one rule before writing any import code: the new system must be able to prove it holds the same financial data as the old one, and deployment must stop if it can't.

1. An ETL you can run again and again

The migration tool is idempotent. Running it a second time updates what it already imported instead of duplicating it. That turned the migration from a one-shot event into something I could rehearse many times against fresh copies of production data.

2. A dry-run mode

Every import command supports a --pretend mode. It runs the full transformation and validation, reports what would change, and writes nothing. Most data problems were found here — long before anyone was affected.

3. A reconciliation gate

After each import, an automated reconciliation compares the old and new systems: invoice totals, payments and outstanding balances. If any financial mismatch is found, deployment is blocked. The final cut-over passed this gate with zero mismatches.

RULE OF THUMB A migration is done when a machine says the numbers match — not when the import finishes without errors.

Bugs the old system was hiding

Reconciling to the last unit exposed problems that had lived in the legacy code for a long time:

  1. Payroll recharged settled dues. I rebuilt the logic with historical, row-based recalculation and covered it with regression tests.
  2. Reports didn't match invoices. Report values are now reconciled against invoice-level breakdowns, down to the smallest unit.
  3. Silent eager-loading errors. Partially loaded ORM models produced wrong financial calculations without throwing errors. The fix was a rule: every decision-critical financial operation loads full entities, with regression tests to keep it that way.

Permissions for a hierarchy

Field sales runs as a hierarchy, so simple role-based access was not enough. Permission checks ("can this role do this action?") and row-level scope ("which records can this person see?") are enforced separately, and automated access-matrix tests check every combination.

Takeaways

  • Make the migration repeatable, then rehearse it.
  • Always have a dry run that writes nothing.
  • Gate deployment on automated reconciliation, not on confidence.
  • Expect the migration to find old bugs — budget time to fix them.
