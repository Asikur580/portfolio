Daiki ERP — CRM & Service Contract Module

A CRM module built inside a multi-company ERP system for an industrial water-treatment and maintenance business. It manages the complete lifecycle of service contracts: agreements, renewals, repair quotations, chlorine supply operations, invoicing, and payment collection.

My role
Backend Developer (sole owner of CRM module)
Replaced
Manual spreadsheet-based workflow
Stack
Laravel 9 · MySQL · Redis · Docker

My Role

Before this module, contract tracking, customer approvals, and payment follow-ups were handled manually in spreadsheets. I owned the backend of the CRM module end to end.

  • Designed the full database architecture and relationships
  • Built REST APIs for all CRM operations
  • Implemented the approval workflow state machine
  • Developed the notification and reminder system
  • Designed the RBAC permission structure (37+ permissions)
  • Worked closely with the frontend team on API contracts
  • Built the reporting and export system

Key Challenges & Solutions

Problems I ran into while building the module, and how I fixed them.

Multi-Company Data Isolation

Early versions had cross-company data leakage.

Solution: a strict company-scoped query layer applied globally across all endpoints, so data stays safe even under filtering.

Duplicate Reminders

Global scheduled reminders caused duplicates or missed alerts.

Solution: per-agreement persisted reminder rows with idempotent execution.

Business Logic Duplication

Frontend and backend both handled approval logic, causing inconsistencies.

Solution: all rules moved to backend computed flags, making the API the single source of truth.

Email Blocking API Responses

Synchronous email sending slowed API responses.

Solution: all notifications migrated to queued jobs with background processing.

Separate Approval Logic per Module

Each module had its own approval logic.

Solution: a polymorphic approval API (type / id) for unified workflow handling.
