Resolving approval workflows with a precedence engine

Asikur Rahman Sep 2026 5 min read

In the Daiki ERP, one approval engine handles 10 request types — payments, travel, expenses, advances, manpower requisitions, purchases and budgets. It replaced paper forms, email chains and Kissflow. The hardest part was not the approvals themselves. It was deciding which workflow a request should follow.

Too many valid answers

Admins could define workflows for a branch, for a department, or for a designation. That flexibility was the requirement — but it meant one request often matched several definitions at once. Depending on which one the code found first, the same kind of request could be routed to different approvers.

Inconsistent routing is worse than slow routing: people stop trusting the system and go back to email.

One order, decided once

I replaced the ad-hoc lookups with a single resolution engine that walks a fixed 12-level precedence order, from the most specific match to the most general. The first level that matches wins. Every request type goes through the same resolver, so the answer to "why did this go to that person?" is always the same list, in the same order.

DESIGN NOTE When configuration can overlap, make precedence explicit and put it in one place. Don't let query order decide business rules.

Bugs that only showed up later

Once routing was stable, four quieter problems surfaced:

  1. Cross-chain condition leakage. Step conditions leaked into other workflow chains that used the same step order. Fix: strict scope matching per chain, so a condition only applies inside its own chain.
  2. Ledger consistency. A failed budget-ledger write could roll back an approval that had already happened. Fix: the ledger is decoupled from the approval transaction, so a ledger failure never breaks the approval flow.
  3. Wrong company context. Some calculations and dashboards used the current user's company instead of the request's. Fix: every service scopes explicitly by the request owner.
  4. Test vs production drift. The "test this chain" feature did not behave like real execution. Fix: both now run through one shared chain-walker engine.

Budgets on data that had none

Budget control was added after projects already existed with no budget structure. Rather than forcing a data migration first, I added a backward-compatible validation layer with safe fallback paths. New projects get full budget checks; old ones keep working until they are updated.

Takeaways

  • Flexible configuration needs a strict, documented resolution order.
  • Scope every rule to where it was defined — chain, company, request owner.
  • Side effects like ledgers should not be able to undo the main action.
  • A "test mode" is only useful if it runs the exact production code path.
