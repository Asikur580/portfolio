Building a payroll engine that never pays twice

Asikur Rahman Sep 2026 6 min read

Payroll is the one feature where "mostly right" is wrong. When I took ownership of the HR module in Tizaraa's multi-company HRM, I rebuilt the payroll engine from scratch around one rule: running the same cycle twice must give the same result, and never a second payment.

The problem with the old flow

Three things kept producing wrong or unexplainable payslips:

  • A payroll run could be triggered again and create duplicate records, or fail halfway and leave a partial cycle.
  • Promotions and increments changed an employee's salary in place, so recalculating an old month used today's salary.
  • Payroll, reports and exports each counted attendance their own way, so the numbers drifted apart and HR reconciled them by hand.

1. Make cycle generation idempotent

Each payroll cycle is generated inside a database transaction. Before writing, the engine checks whether a cycle for that company, period and employee already exists. If it does, the run skips or updates it — it never inserts a second one. A failure rolls the whole cycle back, so there is no half-finished state to clean up.

I also store the per-component breakdown of every salary line — basic, allowances, deductions — instead of only the final amount. When someone asks "why is this payslip different from last month", the answer is in the data, not in someone's memory.

RULE OF THUMB If a job can be clicked twice, retried by a queue, or re-run by a cron, design it so the second run is harmless.

2. Effective-dated salaries

Instead of overwriting an employee's salary, every change becomes a new salary assignment with an effective_from date. The payroll engine asks one question: what salary was valid on the days this person actually worked?

That makes mid-cycle promotions correct automatically, and recalculating a past month gives the same result it gave then — which is exactly what auditors expect.

3. One attendance summary engine

The biggest source of disagreement was attendance. I replaced the separate calculations with a single attendance summary engine. Payroll, reports and Excel exports all read from it, so present days, leave, late marks and shift-roster data mean the same thing everywhere.

Manual reconciliation between payroll and attendance stopped being a monthly task, because there is only one number to reconcile.

Access control came with it

Payroll data is sensitive, so the rebuild also fixed who can see and approve what:

  1. A dedicated approval-permission table separates who a request is routed to from who may give the final approval, so managers can no longer approve outside their scope.
  2. A parent-department access layer scopes visibility for department heads, without breaking the existing permission model.

What I'd tell someone building payroll

  • Treat every run as a retry. Idempotency first, features second.
  • Never overwrite money-related history. Add dated rows instead.
  • Keep one source of truth for anything that feeds a salary.
  • Store the breakdown, not just the total.
